## What is a session?

A session represents one complete execution of an agent for a prospect. It is the central object in Nova, tying together an **agent**, a **prospect**, a **channel** (voice, chat, Telegram, etc.), and optionally a **call** or **workflow run**.

When you start a session, Nova:

1. Creates the session record with a unique UUID you provide
2. Appends your `instruction` as the first user message
3. Triggers the configured agent to process the session
4. Fires webhook events as the session progresses and completes

Sessions generated via workflows are created automatically. For custom orchestration - triggering specific agents, passing context, building multi-step flows - use the Start Session API directly.

## Session lifecycle

```
PENDING
   |
   v
ACTIVE -----> COMPLETED
   |
   +---------> STOPPED
   |
   +---------> FAILED
   |
   +---------> CANCELLED
```

| Status | Description |
|--------|-------------|
| `PENDING` | Session created; agent not yet triggered |
| `ACTIVE` | Agent is currently running the session |
| `COMPLETED` | Agent finished successfully |
| `STOPPED` | Session was manually stopped via the Dashboard or API |
| `FAILED` | Agent encountered an unrecoverable error |
| `CANCELLED` | Session was cancelled before it started |

When a session reaches any terminal state (`COMPLETED`, `STOPPED`, `FAILED`, `CANCELLED`), Nova fires a [`session.completed` or `session.failed` webhook event](/webhooks#session-events).

## Session channels

The `channel` field tells you how the session was initiated and which modality the agent used:

| Channel | Description | Notes |
|---------|-------------|-------|
| `voice` | Outbound or inbound phone call | Links to a call record via `call_id` |
| `chat` | Text-based messaging (web widget, API) | No call record |
| `telegram` | Telegram bot interaction | Requires Telegram integration in Dashboard |
| `whatsapp` | WhatsApp messaging | Requires WhatsApp integration |
| `slack` | Slack workspace interaction | Requires Slack integration |

## How sessions are created

Sessions are created in two ways depending on the channel:

| How | Channels | Who creates the session |
|-----|----------|------------------------|
| **API-triggered** | `voice`, `chat` | Your code calls the Start Session API |
| **Gateway-triggered** | `telegram`, `whatsapp`, `slack` | The platform bot creates the session automatically |

### API-triggered sessions (voice and chat)

For voice and chat channels, your code creates sessions explicitly using the Start Session API. You control when the session starts, which agent runs, and what instruction it receives.

### Gateway-triggered sessions (Telegram, WhatsApp, Slack)

For text-based channels, sessions are created automatically by the platform gateway when a user sends a message to your connected bot. You do not call the Start Session API for these - the gateway handles session creation on behalf of the user.

**How it works:**

```
User sends message to Telegram bot
           │
           ▼
Cozmo platform gateway receives the message
           │
           ▼
Gateway auto-creates a session (channel: telegram)
           │
           ▼
Agent processes the session and replies via the bot
           │
           ▼
session.completed webhook fires when conversation ends
```

To enable this, connect a Telegram (or WhatsApp/Slack) bot to an agent in the Dashboard under **Agent → Integrations**. Once connected, every inbound message to that bot starts a new session for that agent automatically.

**What you can still do via API:**
- `GET /agent-sessions/{session_id}` - retrieve the session status and metadata
- Receive `session.completed` / `session.failed` webhook events just like API-triggered sessions

<Info>
  The `session_id` for gateway-triggered sessions is generated by the Cozmo platform, not by your code. Retrieve it from the webhook payload's `data.session_id` field.
</Info>

## Starting a session

The Start Session endpoint creates and immediately triggers a session. You must provide a **client-generated UUID v4** as `session_id` in the URL path. This makes the operation idempotent - retrying with the same ID never creates a duplicate.

<CodeGroup>

```bash cURL
curl -X POST \
  "https://v2-nova-api.prod.czmx.in/api/org/{org_id}/agent-sessions/{session_id}/start" \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "agentId": "agt_01j9xyz",
    "instruction": "Follow up with this prospect about their enterprise demo request. They are interested in the Professional tier and have a budget of $50k/year.",
    "title": "Enterprise demo follow-up - Jane Doe",
    "prospectId": "5abb08f3-c2d7-44c1-9fb0-8bb7bb4aa66e",
    "source": "crm-integration"
  }'
```

```go Go
package main

import (
    "bytes"
    "encoding/json"
    "fmt"
    "log"
    "net/http"
    "os"

    "github.com/google/uuid"
)

func StartSession(orgID, agentID, prospectID, instruction, title string) (string, error) {
    sessionID := uuid.New().String() // Generate before request

    payload, _ := json.Marshal(map[string]string{
        "agentId":     agentID,
        "instruction": instruction,
        "title":       title,
        "prospectId":  prospectID,
        "source":      "go-integration",
    })

    req, _ := http.NewRequest("POST",
        fmt.Sprintf("https://v2-nova-api.prod.czmx.in/api/org/%s/agent-sessions/%s/start", orgID, sessionID),
        bytes.NewReader(payload),
    )
    req.Header.Set("X-API-Key", os.Getenv("NOVA_API_KEY"))
    req.Header.Set("Content-Type", "application/json")

    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        return "", fmt.Errorf("start session: %w", err)
    }
    defer resp.Body.Close()

    if resp.StatusCode == http.StatusConflict {
        // Idempotent - session already started with this UUID
        return sessionID, nil
    }
    if resp.StatusCode >= 400 {
        return "", fmt.Errorf("nova API error %d", resp.StatusCode)
    }

    var result map[string]string
    json.NewDecoder(resp.Body).Decode(&result)
    return result["sessionId"], nil
}
```

## Idempotency

The Start Session endpoint is idempotent on `session_id`. If you call it twice with the same UUID, only one session is created and the same `sessionId` is returned both times.

**Why this matters:** If your request times out or the network drops before you receive the response, you do not know whether the session was created. Without idempotency, retrying would create a duplicate session and place two calls to the same prospect.

**Pattern:** Generate the UUID before making the first request. Store it in your database before sending the request. On any retry, use the same UUID.

```python Python
import uuid
import requests

def start_session_safe(org_id: str, payload: dict) -> str:
    """Start a session with safe retry on transient failures."""
    session_id = str(uuid.uuid4())

    # Persist session_id to DB before making the request
    # db.save_pending_session(session_id, payload)

    url = f"https://v2-nova-api.prod.czmx.in/api/org/{org_id}/agent-sessions/{session_id}/start"
    headers = {"X-API-Key": "YOUR_API_KEY"}

    for attempt in range(3):
        try:
            resp = requests.post(url, headers=headers, json=payload, timeout=30)
            if resp.status_code == 409:
                # Session already started - idempotent success
                return session_id
            resp.raise_for_status()
            return resp.json()["sessionId"]
        except requests.HTTPError as e:
            if e.response.status_code < 500:
                raise  # Don't retry 4xx
            if attempt == 2:
                raise
```

## Create Session vs Start Session

Nova has two session creation endpoints. Understanding which to use:

| Endpoint | Creates session? | Triggers agent? | Use when |
|----------|-----------------|-----------------|----------|
| **Start Session** (`POST /agent-sessions/{id}/start`) | Yes | Yes | You want to run an agent right now |
| **Create Session** (`POST /agent-sessions`) | Yes | No | You need to pre-create a session record before it runs, or associate it with a call/workflow run upfront |

For most integrations, **Start Session** is the right choice. Use Create Session when building advanced orchestration where you need to prepare the session object before triggering it.

### The external_refs pattern

Use `external_refs` to link sessions to records in your other systems. This makes it easy to look up sessions from your CRM, helpdesk, or data warehouse:

```json
{
  "external_refs": {
    "salesforce_contact_id": "003Hs00000ABC",
    "hubspot_deal_id": "12345678",
    "zendesk_ticket_id": "TKT-9902",
    "internal_lead_id": "lead_xyz"
  }
}
```

When your webhook fires, `external_refs` is included in the session data, so your handler can immediately find the matching record in any external system without a database lookup.

## Waiting for session completion

### Webhook (recommended for production)

Configure a webhook endpoint in [Dashboard - Webhook Settings](https://dash.prod.czmx.in). Nova fires `session.completed` or `session.failed` as soon as the session reaches a terminal state.

```python Python (FastAPI)
from fastapi import FastAPI, BackgroundTasks, Request

app = FastAPI()

@app.post("/webhook/cozmo")
async def receive_webhook(request: Request, background: BackgroundTasks):
    payload = await request.json()
    background.add_task(handle_event, payload)
    return {"ok": True}

async def handle_event(payload: dict):
    event = payload["event"]
    data = payload["data"]

    if event == "session.completed":
        session_id = data["session_id"]
        call_id = data.get("call_id")
        duration = data.get("duration_seconds")
        external_refs = data.get("external_refs", {})

        print(f"Session {session_id} completed. Call: {call_id}. Duration: {duration}s")

        # If the session had a call, fetch the full call record
        if call_id:
            call = await fetch_call(call_id)
            await update_crm_from_call(call, external_refs)

    elif event == "session.failed":
        print(f"Session failed: {data['session_id']} - {data['status']}")
```

### Polling (development only)

For local testing, poll the session status until it reaches a terminal state:

```python Python
import time

def wait_for_session(org_id: str, session_id: str, timeout: int = 300) -> dict:
    deadline = time.time() + timeout
    while time.time() < deadline:
        session = requests.get(
            f"https://v2-nova-api.prod.czmx.in/api/org/{org_id}/agent-sessions/{session_id}",
            headers={"X-API-Key": "YOUR_API_KEY"},
        ).json()
        if session["status"] in ("COMPLETED", "STOPPED", "FAILED", "CANCELLED"):
            return session
        time.sleep(5)
    raise TimeoutError(f"Session {session_id} did not complete within {timeout}s")

session = wait_for_session(ORG_ID, session_id)
print("Final status:", session["status"])
```

## Session to call relationship

For voice sessions, the `call_id` field links the session to its call record. The relationship is one-to-one: each voice session has at most one call.

```
workflow_run --> session (channel: voice)
                    |
                    v
                  call (transcript, evaluations, recording)
```

To get the full call details after a session completes:

```python Python
def get_call_for_session(org_id: str, session_id: str) -> dict:
    session = requests.get(
        f"https://v2-nova-api.prod.czmx.in/api/org/{org_id}/agent-sessions/{session_id}",
        headers={"X-API-Key": "YOUR_API_KEY"},
    ).json()

    call_id = session.get("call_id")
    if not call_id:
        return None

    return requests.get(
        f"https://v2-nova-api.prod.czmx.in/api/org/{org_id}/calls/{call_id}",
        headers={"X-API-Key": "YOUR_API_KEY"},
    ).json()
```

  </Card>
  <Card title="Pass context in instruction" icon="pencil">
    Be specific in the `instruction` field. Include the prospect's context, the goal of the session, and any constraints. A generic instruction like "call the prospect" produces worse results than "follow up with Jane about her $50k enterprise deal - she mentioned interest in the Professional tier but had questions about SLA".
  </Card>
  <Card title="Use metadata for campaign tracking" icon="chart-bar">
    Pass campaign, cohort, and source identifiers in `metadata`. These pass through to webhook payloads so you can segment and analyze session outcomes by campaign without any extra lookups.
  </Card>
</CardGroup>
